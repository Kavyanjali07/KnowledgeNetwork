Social:
- createPost frontend: POST /social/posts with body { workspaceId, content, entityType, entityId } -> Backend SocialController.createPost expects request params, not body: @PostMapping("/posts") with @RequestParam UUID workspaceId, @RequestParam String content, @RequestParam String entityType, @RequestParam UUID entityId
  -> MISMATCH: Frontend uses POST body, backend expects request params (query/form). However api-client post serializes JSON body; Spring will not map JSON body to @RequestParam. Need to adjust frontend to send as query params OR adjust backend to accept @RequestBody.
- getPosts frontend: GET /social/posts/{workspaceId} -> Backend @GetMapping("/posts/{workspaceId}") expects PathVariable workspaceId and optional page/size -> OK
- likePost frontend: POST /social/posts/{postId}/like with body { workspaceId } -> Backend @PostMapping("/posts/{postId}/like") has only @PathVariable postId and AuthenticationPrincipal -> It doesn't accept workspaceId param. Frontend sends workspaceId in body; backend ignores it. Either frontend should not send body or backend should accept request param. POST with body may be ignored but Spring may reject if body present and controller expects none. However current backend method signature has no @RequestBody so request body will be ignored. But api-client sends JSON body; Spring should still accept the request. Still it's better to send workspaceId as request param for consistency.
- unlike/favorite/unfavorite similar patterns -> Backend methods accept PathVariable and AuthenticationPrincipal only.
- addComment frontend: POST /social/posts/{postId}/comments with body { workspaceId, content, parentCommentId } -> Backend expects @RequestBody SocialCommentRequest (which likely has content and parentCommentId) and path postId. It does not expect workspaceId; frontend sends workspaceId which will be extra in JSON body; Spring will bind fields present in JSON that match Java fields and ignore extras -> OK
- addTag frontend: POST /social/posts/{postId}/tags with body { workspaceId, tag } -> Backend expects PathVariable postId and @RequestParam tag -> MISMATCH: frontend sends JSON body; backend expects request param. Call will fail to map tag.
- followUser frontend: POST /social/follow with body { workspaceId, followeeId } -> Backend expects @RequestParam UUID followeeId -> MISMATCH: frontend sends JSON body; backend expects request param.
- getSummary frontend: GET /social/posts/${postId}/summary with params { workspaceId } -> Backend @GetMapping("/posts/{postId}/summary") expects only PathVariable postId -> It ignores workspaceId param -> OK

Notifications:

- getUnreadCount: GET /notifications/unread-count -> Backend GET returns Long -> frontend expects { count: number } -> MISMATCH: backend returns ApiResponse<Long> with raw number; frontend expects object { count } -> Need to adapt frontend to use response.data (number) not response.data.count.

So implement `patch` in api-client and use it from notificationApi.markAsRead.

Conclusions:
- Many endpoints align. Issues found:
  1) Social createPost expects RequestParams, frontend sends JSON body. Adjust frontend socialApi to send as params.

  3) Notifications markAsRead uses PATCH; add `patch` helper to `api-client` and update frontend to call it.
  4) notificationApi.getUnreadCount frontend expects `{ count }` but backend returns raw number. Update frontend to adapt.
